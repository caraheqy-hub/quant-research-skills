# 错题本：已观察的问题

按关键词查相近案例；这里的条目是排查线索，不替代本次日志与复现。新增问题用“症状、证据、原因状态、修复、验证、预防”六项记一条，具体项目的冗长日志留在项目里。

## Python / GM 环境

### `collections.MutableMapping`，旧 `get-pip.py`

- **症状**：掘金安装脚本的 `get-pip.py` 抛 `AttributeError: module 'collections' has no attribute 'MutableMapping'`；同一输出随后显示 `Requirement already satisfied: gm ... (3.0.187)`，最后出现“请按任意键继续”。
- **证据**：对话中用户提供的 traceback 和安装输出。`get-pip.py` 从临时 `pip.zip` 导入旧实现。
- **原因状态**：旧安装引导脚本与所选 Python 的 `collections` API 不兼容是有力推断；未取得该脚本完整版本、解释器路径和安装器退出码，不把整次 SDK 安装失败归因于按 Enter。
- **处理**：先用目标解释器运行 `python -m pip --version`、`python -c "import gm; print(gm.__version__)"`，再决定是否需要更新 pip 或 gm；安装只用该解释器的 `-m pip`。按 Enter 只结束暂停，不解释先前异常。
- **验证**：必须确认同一解释器能导入 gm，并运行只读最小 API 调用；此案例当时仅从 `Requirement already satisfied` 不能证明完整 SDK 可用。
- **预防**：在多 Conda 环境机器上记录 `sys.executable`、`python --version`、`python -m pip --version`，不要只看系统的 `pip`。

### 多 Python 环境选错解释器

- **症状**：掘金 UI 列出 Anaconda base 3.13 和五个 3.11 Conda 环境，SDK 的安装目标容易与回测解释器不同。
- **证据**：用户提供的安装界面；并无证据证明这次回测确实选错。
- **原因状态**：风险线索，非已确诊故障。
- **处理与验证**：对 UI 选中的路径、终端 `sys.executable`、`gm.__file__` 和策略启动日志逐一对齐；只保留真正需要的环境，删除前先核对依赖项目。
- **预防**：项目 README 明确解释器与安装命令，优先复用既有、已验证环境。

### Windows 控制台编码与中文 skill 校验

- **症状**：读取包含中文的 skill 文件时，校验脚本在默认系统编码下抛解码错误。
- **证据**：本次运行 `quick_validate.py` 时遇到 GBK 解码失败，设置 `PYTHONUTF8=1` 后通过。
- **原因状态**：确认是校验脚本的文本编码依赖与 UTF-8 文件不一致；不是 skill 内容格式错误。
- **处理与验证**：在该命令的环境中设置 `PYTHONUTF8=1`，重新运行校验并确认通过。
- **预防**：文本工具显式使用 UTF-8；跨平台脚本和 CI 固定编码。

### Windows 终端输出 PDF 提取文本失败

- **症状**：PDF 文本已经提取，但打印包含特殊连字时终端输出编码报错。
- **证据**：本次用 `pypdf` 提取简历时，默认输出编码不能表示某些字符；将 `sys.stdout` 设为 UTF-8 后可读取。
- **原因状态**：确认是终端输出编码问题，不能据此判断 PDF 读取失败。
- **处理与验证**：`sys.stdout.reconfigure(encoding="utf-8")` 后重跑；同时检查提取内容是否完整。
- **预防**：PDF 提取与日志输出分别排查，避免把显示错误误判为文件损坏。

### 沙箱内 GitHub CLI 网络访问失败

- **症状**：本次 `gh repo list` 在默认沙箱网络下失败。
- **证据**：同一只读命令在允许网络的执行权限下成功，显示当前账号及仓库。
- **原因状态**：确认是执行环境的网络边界，不是仓库不存在或 GitHub 登录失效。
- **处理与验证**：先检查 `gh auth status`；对用户授权的网络操作申请合适的执行权限，再重试原命令。
- **预防**：区分认证、DNS/网络、仓库权限三种错误；不要通过反复修改仓库配置排查网络限制。

### 沙箱创建的 Git 仓库在普通用户权限下显示 `dubious ownership`

- **症状**：工作目录里有 `.git` 且沙箱中可以提交；切换到有网络权限的执行环境后，`gh repo create --source .` 误报当前目录不是 Git 仓库。
- **证据**：同一目录的 `git status` 显示 `detected dubious ownership`；沙箱与当前 Windows 用户的目录所有者 SID 不同。给该次命令设置精确的 `safe.directory` 后，建仓与推送成功。
- **原因状态**：已确认 Git 的目录所有权保护阻止了 CLI 识别仓库，不是 `.git` 缺失。
- **处理与验证**：先检查 `git status` 的实际错误；只给当前仓库进程设置 `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_0=safe.directory` / `GIT_CONFIG_VALUE_0=<已核实的仓库绝对路径>`，再重试原命令并核对远端分支。
- **预防**：权限环境切换后，先区分网络、仓库所有权和认证问题；避免用全局 `safe.directory=*` 关闭保护。

## 掘金回测

### “按任意键继续”后回测无绩效

- **症状**：窗口暂停后关闭，UI 提示“绩效分析失败：当次回测无交易，无绩效数据”。
- **证据**：用户截图与描述；缺少策略完整运行日志、订单事件与退出码。
- **原因状态**：未确诊。暂停提示不是根因。可能是策略从未发单、发单被拒、数据未到或在发单前报错，不能凭 UI 文案选择其一。
- **处理**：核对启动解释器、策略日期和代码；捕获完整 stdout/stderr、`init/on_bar` 是否触发、订阅数据量、信号条件、订单回执、资金与交易时段。先跑只读数据查询，再跑最小回测。
- **验证**：至少观察到预期事件和订单状态；只见终端关闭或 `gm` 已安装都不算修好。
- **预防**：保留诊断日志，错误时显示完整异常；对“零交易”和“程序崩溃”分别报告。

### 第三方策略模板遮蔽 `order_value`

- **症状**：检查已安装第三方 `juejinquant` 模板发现先写 `order_value = available * POSITION_PCT`，随后调用 `order_value(...)`。
- **证据**：本地该 skill 的示例源码；这是静态审查发现，未宣称真实策略已触发。
- **原因状态**：确认的名称遮蔽缺陷；变量变成数字后不可调用。
- **处理与验证**：若采用该示例，将金额变量改为 `target_amount`，用官方文档确认 API 签名，再在隔离回测中走到买入分支。
- **预防**：第三方 skill 示例先审查，再移植；避免把 API 名字用作局部变量。

## 因子研究

### 不同窗口比较使用不同日期

- **症状**：10/20/40 日候选按各自可用日期比较，较长窗口少了早期样本，选优可能受日期而非公式影响。
- **证据**：QR 项目华福成交量因子调参记录；对齐 55 个交易日后数值与筛选口径变化。
- **原因状态**：确认的实验设计偏差。
- **处理与验证**：先确定最长预热窗口，再只在共同日期及同一股票池比较所有候选，保存全部试验。
- **预防**：筛查输出记录 `common_dates`、首尾信号日与候选覆盖率。

### 缺失交易日造成错误的“下一日”收益

- **症状**：某证券缺失一日行情时，按该证券逐行 `shift(-1/-2)` 会跨过市场交易日，将较远价格误作下一交易日成交。
- **证据**：QR 项目 `test_missing_session_cannot_be_skipped_in_next_open_return`。
- **原因状态**：确认的时间对齐缺陷。
- **处理与验证**：将每只证券的下一/再下一日期与全市场交易日历核对，不一致的标签置缺失；原测试通过。
- **预防**：每次换数据源或频率时重跑缺失日与执行时点测试。

### 用全期完整性筛股票造成未来信息选择

- **症状**：先看完整样本期，剔除全期缺一根日线的股票，再回测早期信号。
- **证据**：华福实验中 23 只静态名单剔除 1 只后做了 22 只研究，报告已披露此规则。
- **原因状态**：确认的方法偏差，不是程序异常。
- **处理**：仅把现有结果当公式级演示；严谨研究按当时可投资条件动态生成股票池，并把不可交易日单独处理。
- **验证与预防**：审计每个信号日的成员资格和数据可见时点；不要把静态小样本收益表述为全 A 股或实盘结果。
