# Project start

Use the same initial workflow for personal engineering and research projects. Scale its depth to the decision; a small project may need only a brief note.

1. **Frame the project.** Identify the intended artifact or research claim, intended user, constraints, available data and compute, success criterion, and the largest uncertainty. Separate what the user has decided from assumptions to test.
2. **Survey precedents once.** Search original papers, official documentation, maintained code, and comparable projects as appropriate. Record source, date/version, license or data restrictions, what was demonstrated, and what remains unknown. Use `source-research` for a broad survey. Reuse this evidence when implementation begins; do not repeat the same survey merely because another skill is activated.
3. **Choose a domain.** Classify by the central uncertainty and method, rather than by a keyword or the eventual programming language. A project can use several skills: select one primary domain workflow and add secondary skills only for concrete subtasks. Use `quant-projects` for market data, signals, strategies and backtests; `agent-development` for tool-using systems; `llm-finetuning` for changing model weights; `ai-system-evaluation` when comparative measurement is the main deliverable. Use `project-craft` for substantial implementation after the initial decision.
4. **Decide whether a new domain is justified.** Reuse a current domain or a project note when its method fits. Propose a new domain skill only when a distinct workflow will recur across projects, has different evidence or validation needs, and would change future decisions. Do not create a domain just because the topic is new. Apply the same test before splitting a domain into platform, asset, model, or task subskills; keep changing API details in focused references or existing platform skills.
5. **Leave a launch note.** Capture the question, expected deliverable, evidence map with source links, closest precedents and gaps, selected domain and why, baseline, first smallest test, acceptance criterion, open risks, and the next decision point. Keep project-specific facts in the project, not in a reusable skill. If evidence is insufficient, identify the cheapest informative experiment.

At a meaningful milestone, use `skill-garden` when an observed lesson may recur across projects. Keep one-off facts in the project and do not make speculative skills during the launch survey.
